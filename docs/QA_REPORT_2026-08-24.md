## 2. Findings

### F-01 — Department Head with no department reads every pending leave company-wide
**Critical · access control · `leaves`** · **FIXED**

**Cause:** `backend/leaves/views.py:49-51`

```python
review = Q(status=Leave.Status.PENDING)
if user.department_ref_id:
    review &= Q(user__department_ref_id=user.department_ref_id)
```

The narrowing clause is applied **only if** the head has a department. With none,
the review clause degrades to "every pending leave row in the organisation".
It fails **open**.

**Why this is reachable, not theoretical:** `backend/users/models.py:86-89` declares
`department_ref` as `on_delete=SET_NULL`. Deleting or merging a Department nulls it
for **every member at once**, so a routine admin action silently promotes every
Dept Head in that department to company-wide read of pending leave.

**This is an outlier, not house style.** The sibling modules apply the same filter
*unconditionally* and are correct:
- `backend/attendance/views.py:206` — `filter(employee__department_ref_id=request.user.department_ref_id)`
- `backend/attendance/policy/views.py:130` — same shape for WFH

**Reproduction:**
```bash
./run-tests.sh leaves/tests/test_checker_department_scope.py
```
```
FAILED leaves/tests/test_checker_department_scope.py::
       test_head_without_department_must_not_see_other_departments_pending
```
The companion test in the same file (head *with* a department) passes, isolating
the cause to the null branch.

**Observed:** a `checker` whose `department_ref` is NULL receives another
department's pending leave in `GET /api/v1/leaves/`.
**Expected:** no department ⇒ no review scope (empty), never unrestricted.

**Suggested fix:** make the filter unconditional, matching attendance — a head with
no department should get an empty review queue, not a global one.

### F-02 — `run-tests.sh` reported success while running zero tests
**Critical · gate integrity · tooling** · **FIXED**

**Cause:** `run-tests.sh:111` (original) — `"${PYTEST_ARGS[@]}"` on an **empty** array is
an "unbound variable" fatal error under `set -u` in bash < 4.4. macOS ships bash
**3.2.57** as `/bin/bash`, which is what `#!/usr/bin/env bash` resolves to. The `cleanup`
EXIT trap then ended in `|| true`, overwriting the status, so the script exited **0**.

**Reproduction (bash 3.2):**
```
with trap:    ARR[@]: unbound variable → cleanup ran → EXIT=0   ← masked
without trap: ARR[@]: unbound variable → EXIT=1
```

**Scope — stated precisely:** this is *not* a universal failure-masking bug. A genuine
command failure (`false`) still exits 1; only the `set -u` fatal path was masked.
**CI is unaffected** — `.github/workflows/ci.yml:69` invokes `pytest` directly on
ubuntu (bash 5.x).

**Observed:** `./run-tests.sh` on macOS printed "pytest on PostgreSQL (0 extra args)",
ran nothing, and exited 0 — a false green from the script written to prevent false greens.
**Expected:** run the suite; propagate failure.

**Fix applied:** `${PYTEST_ARGS[@]+"${PYTEST_ARGS[@]}"}` (safe on every bash) and
`cleanup()` now captures `$?` first and re-exits with it. Both verified under bash 3.2:
empty expansion survives, args still pass through, and a failure now yields EXIT=1.

### F-03 — Responsive gate is Linux-only and hangs on macOS
**Major · gate integrity · tooling** · **FIXED**

**Cause:** `frontend/qa/shell-scroll.test.mjs:26`, `qa/safe-area.test.mjs:41`,
`qa/capture.sh:21` hardcoded `/usr/bin/google-chrome`. Supplying the correct macOS path
did not fix it: **Chrome ≥132 on macOS writes `--dump-dom` output and then never exits**,
so `spawnSync` blocked forever (verified: DOM correct, process alive after 30 s).

**Observed:** all 8 widths reported `FAIL — page did not render` (reads as a layout
regression), then the run hung.
**Expected:** either run, or fail with "Chrome not found".

**Fix applied:** new `frontend/qa/chrome.mjs` — cross-platform binary resolution plus a
`dumpDom()` that resolves on `</html>` rather than process exit, and cleans up its
profile with retries. Wired into both node harnesses; `capture.sh` got the equivalent
in bash (per-call profile, wait-for-output, `--screenshot` handled by size-stability).

**Result after fix — no responsive regression exists:**

### F-04 — `capture.sh` failed every screen on macOS via a GNU-only regex
**Major · gate integrity · tooling** · **FIXED**

**Cause:** `frontend/qa/capture.sh:190` and `:228` used `sed -n 's/.*, \([0-9]\+\) chars.*/\1/p'`.
`\+` is a **GNU extension**; BSD/macOS sed returns **empty**.

**Consequences, both silent:**
1. `capture_line` never saw a char count, so **every screen was captured 3×** (the retry
   ceiling) — this was the 10-minute timeout, not slowness.
2. The count check then reported `SUSPICIOUS: only 0 characters rendered` and set
   `fail=1` for **every screen**, so the gate **always failed on macOS regardless of layout**.

**Reproduction:**
```bash
printf '%s' "[dashboard @ 390px, 1991 chars] NO OVERFLOW FINDINGS" \
  | sed -n 's/.*, \([0-9]\+\) chars.*/\1/p'      # BSD sed → (empty); GNU sed → 1991
```

**Fix applied:** `[0-9][0-9]*` (POSIX BRE, correct on both). Gate now reports
`[dashboard @ 390px, 1991 chars] NO OVERFLOW FINDINGS` with no retries, and exits 0.

### F-05 — Admin user edits are audited with an empty `changes` payload
**Major · data integrity / audit · `users`** · **FIXED**

**Cause:** `backend/users/admin_views.py:56-58`
```python
def perform_update(self, serializer):
    serializer.save()
    log_action(self.request.user, AuditLog.Action.UPDATE, instance=serializer.instance, request=self.request)
```
No `changes` argument, and `backend/audit/services.py:29` stores `changes=changes or {}`.

The row records actor, timestamp, target and IP — but **nothing about what changed**.
This is the highest-privilege mutation surface: the same PATCH sets `is_active`,
`department_ref`, and `employee_type` (which grants real authority — see F-06).

**Reproduction:**
```bash
./run-tests.sh users/test_admin_update_audit.py
```
```
FAILED users/test_admin_update_audit.py::test_admin_update_of_employee_type_is_recorded_in_the_audit_row
E   AssertionError: admin user update wrote an audit row with an EMPTY changes payload
E   assert {}
```
The control test in the same file **passes**, showing the standard already exists:
`change-role` (`admin_views.py:196-207`) records `{'from': ..., 'to': ...}`.

**Observed:** `changes == {}`. **Expected:** at minimum the changed field names, ideally
before/after as `change-role` already does.

**Suggested fix:** pass `changes={'event': 'USER_UPDATED', 'fields': sorted(serializer.validated_data)}`
(plus before/after for authority-bearing fields) in `perform_update`.

### F-06 — `employee_type` grants authority independently of `role`
**Major · access control · `memos`, `inventory`** · **OPEN — needs a product decision**

Per the brief, permissions must derive from `role` only. Two sites gate on org rank:

- `backend/memos/governance.py:328` — `can_manage_assignments` returns True for
  `employee_type in {SUPERVISOR, MANAGER, DEPARTMENT_HEAD, HR_OFFICER}`
- `backend/inventory/roles.py:91` — `is_supervisor` is "rank OR role"

**Concretely:** a user with `role='maker'` — displayed as **Employee**, the lowest
permission level — may declare absences and move workflow steps on *another author's*
memo purely because HR set their org-rank field.

**Reproduction:** `./run-tests.sh memos/tests/test_employee_type_authority.py` — both tests pass,
documenting the behaviour (`role='maker'` + `employee_type='supervisor'` ⇒ authority;
plain employee ⇒ none).

**Both sites are documented as deliberate** (Phase 49 / 49.5 audits), so I wrote these as
**characterization** tests rather than asserting my judgement over a design decision.
They fail loudly if the behaviour changes, and are the failing case to fix against if the
`role`-only invariant is meant to hold.

**Not self-escalatable** — `SelfProfileSerializer` (`users/serializers.py:91-95`) omits
`employee_type`, `role` and `is_active`. It requires an admin PATCH — which is exactly the
call F-05 fails to log.

**Aggravating factor:** `employee_type` has value `department_head` labelled
"Department Head" (`frontend/src/services/roles.js:19`) — the *same label* as `role='checker'`.
A user record can display "Department Head" on the rank axis while carrying Employee
permissions.

**Suggested fix:** decide the invariant. Either drop the `employee_type` branch from both
gates, or amend the brief and keep the characterization tests as the record.

### F-07 — `serial_number` has no uniqueness, and lookup silently picks one
**Major · data integrity · `inventory`** · **FIXED**

**Cause:** `backend/inventory/models.py:141` — `CharField(max_length=120, blank=True, default="")`
with **no** unique constraint on the model or in **any** migration (verified across
`inventory/migrations/`).

**Why it bites:** `backend/inventory/lifecycle_views.py:572-574` resolves a scanned code:
```python
item = InventoryItem.objects.filter(serial_number__iexact=code).first()
```
Two assets sharing a serial ⇒ the scan resolves to an **arbitrary** one, and the holder
permission check at line 585 then applies to the **wrong asset**.

Every neighbouring model gets this right, which makes it look like an omission:
`unique_together ("employee","date")` (attendance), partial-unique active biometric
mapping (`biometric/models.py:301,309`), `uniq_active_assignment_per_item` (inventory).

**Suggested fix:** a partial `UniqueConstraint` on `serial_number` with
`condition=~Q(serial_number="")` — a plain `unique=True` would collide on the blank default.

### F-08 — Signed media URLs are replayable by anyone holding them
**Major · access control · `documents`** · **PARTIALLY FIXED — claim corrected, gap remains by design**

**Cause:** `backend/documents/protected_media.py:76-100`. The module docstring states that
binding the HMAC to a user id means "a leaked link is useless to anyone else". It is not:
`permission_classes = [AllowAny]`, `authentication_classes = []`, and the file contains
**no reference to `request.user`** — `u` is read from the query string and only checked
against the signature.

**Reproduction (live, against the running dev server):**
```
admin-bound link, no auth header  → HTTP 200, file served
same link, 1 byte of sig changed  → HTTP 403
```

**Observed:** the HMAC correctly prevents *forging* a link for another user, but not
*replay* — the exact "pasted chat message / browser history" case the docstring claims to
cover. The only real protection is the 5-minute TTL.
**Expected:** either the claim holds, or it is not claimed.

**Suggested fix:** either a short-lived cookie scoped to `/api/v1/media/` checked against
`u`, or correct the docstring to state that these are time-boxed bearer capabilities.
I did not implement either — it is a design decision, not a typo.

### F-09 — Push endpoint documents a compensating control that does not exist
**Minor · biometric ingest** · **FIXED** *(Minor because the unauthenticated design is
deliberate and network-mitigated; the defect was the false claim.)*

**Cause:** `backend/biometric/push_views.py:17-33` states the unauthenticated `/iclock/*`
path is guarded by "serial allow-list, IP allow-list, **per-serial throttling**".

The first two exist (`_resolve_device`, lines 74-99). The third does not:
`IClockBaseView` extends `django.views.View` (line 43/104), so **DRF throttling cannot
apply**, and `DeviceRateThrottle` keys on `request.auth` being a `BiometricDevice`
(`biometric/throttling.py:33-35`) — only ever true on the HMAC REST path
(`biometric/views.py:240-244`).

With `BIOMETRIC_PUSH_ALLOWED_IPS` defaulting to `''` (`config/settings.py:149` = no IP
restriction), a default deployment's only control is knowing a serial, with **unlimited
guesses**. The unauthenticated protocol is an accepted, well-argued trade-off; the defect
is that a stated mitigation is absent — which is what a deployer reads when judging
residual risk.

**Suggested fix:** implement per-serial rate limiting in `IClockBaseView.dispatch`, or
strike it from the docstring.

### F-10 — Leave decision actions are not race-safe: two reviewers can both grant one leave
**Critical · data integrity / workflow · `leaves`** · **FIXED**

**Cause:** `backend/leaves/views.py` — all three decision actions (`set_status`,
`dept_head_review`, `hr_review`) followed a check-then-act pattern:

```python
leave = self.get_object()                 # unlocked read
if leave.status != PENDING: return 400    # guard, OUTSIDE the transaction
with transaction.atomic():                # transaction opens only now
    ...write...
```

No `select_for_update` existed anywhere in `leaves/views.py`. Two reviewers — or
one double-submitted form — could both read `PENDING`, both pass the guard, and
both write. The second write silently overwrote the first reviewer's identity
and timestamp (`department_head_reviewer`, `approver`, action date), so the
granted leave named the **wrong approver** in the record, the PDF and the audit
trail, and fired duplicate audit rows and notifications.

`inventory/lifecycle.py` has always taken the lock *before* the guard and says so
in its module docstring (line 22: "`select_for_update()` so two actors cannot both
advance it"). The leave engine did not — an oversight, not a decision.

**Reproduction — verified in both directions:**
```bash
./run-tests.sh leaves/tests/test_cluster_b.py::test_two_dept_heads_cannot_both_grant_the_same_leave
```
Against the pre-fix code (two threads released by a barrier):
```
AssertionError: expected exactly one successful grant, got {'b': 200, 'a': 200}
   — both succeeding means the second reviewer overwrote the first
```
With the fix: passes, and the recorded reviewer matches the request that returned 200.

**Observed:** both concurrent approvals returned `200` and both wrote.
**Expected:** exactly one wins; the loser is refused.

**Fix applied:** each action now re-reads the leave with `select_for_update()`
*inside* `transaction.atomic()` and re-evaluates its status guard there. The
pre-transaction check is kept as a cheap pre-filter. The balance itself was never
at risk — it is derived from committed day records rather than incremented
(`services.py:611-662`), which is why this is a workflow/attribution defect
rather than a balance one.

## 5. What I did NOT test, and why

Stated explicitly — an unstated gap is worse than a known one.

**Whole tracks not covered:**
- **Track 3 (leave engine) — entirely untested.** No probing of half-days, backdated
  application, cancellation after approval, carry-forward, mid-year joiners,
  employment-type categories, or the concurrent-approval race. This is the largest gap
  in this report and carries Critical potential.
- **Track 6 (files, exports, rendering) — untested.** No upload type/size/traversal
  probing, no empty/one-row/large export matrix, no WeasyPrint-vs-`html2pdf.js` agreement
  check, and **no XSS testing of TipTap content** (DOMPurify on render vs backend
  sanitisation on store). Note the suite's own attachment-spoofing tests pass now that
  `libmagic` is installed.
- **Track 7 (frontend behaviour) — only the automated gates.** No auth-expiry-mid-form,
  double-click submit, back-button-after-mutation, stale react-query cache, or API-500
  error states. These need a driven browser session, which I did not run.
- **Track 2 — only the BS-calendar cross-check** (clean, 14/14 boundary dates). Punch
  derivation edge cases, DST, policy retroactivity (HR-10), the correction
  approve→apply→revert ledger, holiday/WFH overlap, comp-off double-counting, and all
  collector ingestion cases are **untested**.
- **Track 8** — only the four highest-ranked gaps were written up; ranks 4-7 have no tests.

**Environmental limits:**
- **`env(safe-area-inset-*)` on physical devices cannot be gated headlessly** — `env()`
  resolves to 0 in headless Chrome, as the harness itself reports. Real notch/gesture-bar
  clearance remains unverified.
- **Python version differs from CI.** CI pins **3.10** (`ci.yml:45`); this run used
  **3.14.6**, the only interpreter available here. The suite is green on both as far as
  this run shows, but version-specific behaviour is not ruled out.
- **`qa/device-matrix.mjs` was not run** — it requires Playwright, which is not installed.
- **No load, concurrency or race testing.** The concurrent-approval race in Track 3 and the
  two-approvers-at-once case were reasoned about from code (`select_for_update` is present
  in `inventory/lifecycle.py:320`) but never executed.

**Data limits:**
- The local database contains **one user (admin) and zero biometric punches**. Every
  RBAC finding was proven with test-created fixtures, not against representative data, and
  no biometric behaviour could be exercised end to end.
